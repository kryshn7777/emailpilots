# COMMON Site Brief — Part 01: Product Discovery
> Used in: `/gsd:map-codebase` follow-up and the `/gsd:new-project` questioning stage. Findings go into `.planning/PROJECT.md` / `REQUIREMENTS.md`.

## Before designing or coding anything
1. Scan the entire repository.
2. Inspect application structure, package files, dependencies, routes, assets, components, APIs, backend interfaces, product flows, branding, existing UI, copy, and technical constraints.
3. Run the existing application where possible.
4. Interact with it.
5. Understand exactly what COMMON does, who it is for, what problem it solves, how it works, what makes it different, and what the user ultimately needs to do.
6. Identify the strongest product capabilities that can become visual storytelling.
7. Identify anything currently misleading, weak, generic, confusing, slow, or visually inconsistent.
8. Do not invent product capabilities that do not exist.
9. Do not redesign the product itself unless necessary for integration.
10. Treat the existing codebase as the source of truth.

## Produce an explicit internal understanding of
- the product
- the target user
- the primary problem
- the emotional problem
- the functional problem
- the differentiators
- the strongest proof
- the strongest visual metaphors
- the conversion action (the real one, from the repo's product flow)
- the reasons someone would share the website
- the reasons someone would return to it

## Rule
Do not immediately start coding after the first file scan. Discovery output is documents, not code. Everything above becomes a standing reference for later phases — especially "strongest proof," "strongest visual metaphors," and "conversion action," which directly feed the storyboard (part 03) and conversion phase (part 07).

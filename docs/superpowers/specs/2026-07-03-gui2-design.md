# GUI2 — Landing-Style App Shell (Design Spec)

**Date:** 2026-07-03
**Status:** Approved by user (brainstorming session)
**Branch context:** feat/m4-sequence-ui

## Problem

The landing site's hero mockup ("Email Pilots · Campaign: Q3 Outreach" window — white cards, blue accents, mono chips, live queue) looks nothing like the actual app GUI (dark aviation sidebar theme). We want a second, separate GUI — **GUI2** — that matches the mockup's visual language while preserving **every feature** of the existing GUI, launchable via `LaunchGUI2.bat`. GUI1 must remain the default and completely unchanged (non-breaking additive rule).

## Decisions (user-confirmed)

1. **Stack:** Same-logic re-skin. New `gui2.html` + `src/gui2.css`; reuse `src/main.ts` wholesale. No new dependencies. No React.
2. **Launcher:** `LaunchGUI2.bat` = dev launcher (`set EPT_GUI=2` → `npm run dev`), mirroring `dev-launch.bat`.
3. **Dormant features:** Surfaced in GUI2 only — "Send to All Now" button visible; no-password OAuth/browser sign-in blocks visible. GUI1 keeps both dark.
4. **Layout:** Mockup-style shell — top chrome bar with traffic dots + mono title + live status pill, horizontal tab nav, two-pane dashboard (template/actions left, live queue right).

## Architecture

### New files
| File | Purpose |
|---|---|
| `gui2.html` (repo root) | Second Vite entry. Loads `/src/gui2.css` + `/src/main.ts`. `<body data-gui="2">`. |
| `src/gui2.css` | Full landing-style theme. Self-contained; does not import `style.css`. |
| `LaunchGUI2.bat` (repo root) | `@echo off` / `cd /d %~dp0` / `set EPT_GUI=2` / `npm run dev` |
| `src/__tests__/gui2-parity.test.ts` | ID-parity guard (see Testing). |

### Modified files (minimal diffs)
| File | Change |
|---|---|
| `vite.config.ts` | Add `build.rollupOptions.input = { main: resolve('index.html'), gui2: resolve('gui2.html') }`. Both emit to `dist-vite/`. |
| `electron/main.ts` | In `createWindow()`: `const useGui2 = process.env.EPT_GUI === '2'`. Dev: `loadURL(VITE_DEV_SERVER_URL + (useGui2 ? 'gui2.html' : ''))`. Prod: `loadFile(dist-vite/(useGui2 ? 'gui2.html' : 'index.html'))`. |
| `src/main.ts` | One line: `const SHOW_NO_PASSWORD_TRANSPORTS = document.body.dataset.gui === '2'` (was hardcoded `false`). |

### Untouched
`index.html`, `src/style.css`, all services, IPC surface, preload. GUI1 renders pixel-identical. Normal launch (`npm run dev`, `dev-launch.bat`, packaged exe without env var) loads GUI1.

## The ID Contract (core invariant)

`src/main.ts` (~3,400 lines) drives all behavior by querying element IDs/classes/data-attributes. **Every ID, class, and data-attr that `main.ts` references must exist in `gui2.html` exactly once, with the same tag semantics (form/input/select/checkbox types preserved).** Layout and styling are free to differ; the query surface is not.

## Visual design (landing hero language)

Tokens (from landing/`EmailPiolets 2` palette):
- Background: near-white `#f7f9fc` with subtle grid-paper lines (`linear-gradient` 1px rgba grid, 24px cells); radial soft-blue wash at top.
- Cards: `#ffffff`, `border: 1px solid #e2e8f0` (slate line), `border-radius: 16px`, shadow `0 8px 30px rgb(0 0 0 / 0.04)`.
- Accent blue `#0055ff` (buttons, active tab, links, progress bars gradient to `#2563eb`); soft blue chip bg `#eaf1ff`.
- Status: green `#16a34a`/`#dcfce7` (delivered/safe/SENDING), amber `#f59e0b` (warnings/near-cap), red `#ef4444` (errors/blocked), grey dashed (queued/disabled).
- Type: Inter for UI, JetBrains Mono for emails, `{{tags}}`, file names, counts (`42 / 100`), title-bar text. (Both fonts already loaded by GUI1's font links; gui2.html includes the same font `<link>`s.)
- Icons: keep Material Symbols spans (main.ts injects them in dynamic renders — swapping icon systems would break parity).

Shell composition:
1. **Chrome bar** (top, full width): three traffic dots (decorative), mono title `Email Pilots`, right-aligned live status pill — green pulsing dot + `SENDING` when scheduler active, grey `PAUSED` otherwise. The pill wraps the existing `#status-stat-container`/`#service-status-text`/`#status-toggle-checkbox` elements so `updateStatusUI()` drives it with zero JS changes; clicking it still toggles the scheduler.
2. **Tab nav** below chrome: same `ul.nav-links` + `li[data-view]` list rendered horizontally (roving tabindex + Arrow-key handlers in main.ts are direction-agnostic). "Advanced · optional" section label becomes a subtle divider chip in the tab row.
3. **Content area**: max-width container on grid-paper background; each view's cards restyled white/blue.
4. **Dashboard two-pane** (mockup echo): left column = Quick Actions + Today's Usage + Getting Started/How-it-works; right column = "LIVE QUEUE" card (Today's Schedule list restyled as queue rows with green check/blue pulse/grey dashed markers + usage fraction in mono + paced-delivery progress bar) and Pre-flight card. Hero stat tiles become a compact stat strip above the panes. Same IDs throughout — only placement/CSS changes.
5. **Login gate & modals**: white cards, blue CTAs, mono chips; wizard progress dots in landing blue.

## Data flow / behavior

Unchanged. `main.ts` ↔ `window.electronAPI` (40+ invoke channels + `onLog`/`onStatusChange` events) works identically because the DOM contract is preserved. 60s refresh interval, scheduler auto-restart on edits, CSV → auto bulk-schedule flow, sequence drip state, suppression, per-account usage — all inherited.

GUI2-only behavioral deltas (both via markup/flag, not logic edits):
- `#test-run-btn` has no `display:none` in gui2.html → visible.
- `SHOW_NO_PASSWORD_TRANSPORTS` resolves `true` under `data-gui="2"` → `#login-nopw-block` + `#acct-nopw-block` visible and wired (Microsoft OAuth needs `MS_OAUTH_CLIENT_ID` env to actually work; UI surfaces regardless, errors surface in existing error elements).

## Error handling

- Missing/renamed element in gui2.html = silent feature loss or runtime throw. Mitigated by the parity test (below) — it must run in CI/`npm test` so future GUI1 feature additions fail fast until mirrored in GUI2.
- `EPT_GUI` unset/any other value → GUI1. No new failure modes in electron main.
- Vite multi-entry: `emptyOutDir` already true; both pages share `dist-vite/assets/` — no collision (hashed filenames).

## Testing & verification

1. **`src/__tests__/gui2-parity.test.ts`** (vitest, no jsdom needed): regex-extract from `src/main.ts` all `getElementById('…')` literals, `querySelector('#…')`/`querySelectorAll` ID literals, and `name="…"` radio/checkbox groups used via `getElementsByName`/form access; assert each appears in both `index.html` and `gui2.html`. Also assert gui2.html has `data-gui="2"` and index.html does not.
2. **Existing suite** (`npm test` — accountStore, onboarding, etc.) stays green.
3. **Build:** `npm run build` (or `vite build`) emits `dist-vite/index.html` + `dist-vite/gui2.html`.
4. **Manual walk (per rigorous-QA workflow):** `LaunchGUI2.bat` → login gate renders (or main app if configured) → visit all 7 views, open all 8 modals, add/edit/delete a test recipient, run preview, toggle scheduler, confirm status pill updates, confirm Send-to-All + no-password blocks visible. Then `dev-launch.bat` → confirm GUI1 identical to before (dormant features still hidden).
5. **Visual check:** screenshot GUI2 dashboard next to landing hero mockup — same family (white cards, blue accents, mono chips, queue rows).

## Non-goals

- No changes to services, IPC, scheduler, transports, or data files.
- No React/Tailwind/dependency additions.
- No GUI1 restyling; no removal of GUI1.
- No packaged-build launcher bat (dev launcher only, per decision #2; packaged builds still honor `EPT_GUI=2` if set).
- No new features beyond surfacing the two dormant ones in GUI2.

## Risks

- **ID drift over time** — covered by parity test.
- **CSS-only expectations in main.ts** (e.g. classes toggled expecting GUI1 visuals like `.leaving` toast animation, `.spin`, shake, confetti canvas) — gui2.css must implement every behavioral class main.ts toggles: `.active`, `.leaving`, `.spin`, `.visible`, `.hidden`, `.danger`, health-dot classes, wizard step states, `prefers-reduced-motion` guards. Implementation plan must enumerate these from style.css.
- **Surfaced OAuth without `MS_OAUTH_CLIENT_ID`** — button errors gracefully via existing error paths; acceptable per user decision.
